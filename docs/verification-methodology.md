# 验证方法论：怎么证明内核"没崩"

这份文档只回答一个问题：**你凭什么说内核没崩？**

本课程从 Lab1 开始，判断一个 Lab 是否通过的主要依据都是串口输出——期望的几行字打全了，就算过。这个判据在绝大多数情况下够用，但它有一个**确定性的盲区**：某些失效模式产生的串口输出和成功运行**逐字节相同**。本课程在 Lab6 x86_64 上真实踩到过一次（详见 [Lab6 的"已知缺陷"一节](../labs/lab06-syscall-user/README.md)），而且第一次尝试补救时**用错了检测方法，得到了第二个假阴性**。这份文档记录最终验证有效的判据和它们的适用边界。

## 为什么串口靠不住

串口是一条**只进不出的有损信道**：内核往里写字节，你在外面看。它能告诉你"到某一刻为止一切正常"，但不能告诉你"那一刻之后发生了什么"——因为一个已经死掉的内核和一个活着但没话说的内核，都不再产生任何字节。

本课程所有 Lab 的期望输出都以"内核打完最后一行、然后安静地空转等中断"结尾，`TIMEOUT` 到了就把 QEMU 杀掉（退出码 124）。这个形态恰好把上面那个盲区放到了最显眼的位置：**最后一行之后内核是活着还是死了，串口上完全看不出来。**

只要一个 Lab 的设计允许中断在用户态（CPL=3 / U-mode）期间落下来，就必须用下面的判据补一次检查，不能只看串口。

## 判据一：去掉 `-no-reboot`，看启动横幅有没有重复

最直观，不需要读懂任何日志格式。

```bash
# 在 solution/x86_64 目录下。注意两点：故意不带 -no-reboot；串口写到文件而不是 stdio，
# 否则横幅会和终端输出混在一起没法 grep。
timeout 15 qemu-system-x86_64 -cdrom build/os.iso \
    -serial file:/tmp/vm_serial.txt -display none \
    -d cpu_reset -D /tmp/vm_reset.log

grep -c "CPU Reset"    /tmp/vm_reset.log    # 复位次数
grep -c "Hello OS from" /tmp/vm_serial.txt  # 启动横幅重复次数
```

`timeout` 是必须的：崩溃的内核会无限重启下去，不会自己退出（`timeout` 杀掉它时退出码是 124，这和本课程测试脚本里"正常空转到超时"的 124 是同一个码，所以**退出码本身不能当判据**）。

**判据：启动横幅出现超过 1 次，就是在重启循环。** 内核崩溃后复位会重新进固件、重新加载内核、重新把启动信息打一遍——这个信号比数复位次数更直观，也更难误读。

**读复位次数前必须知道的基线：一次健康的启动本来就有 2 次 `CPU Reset`。** 这是 QEMU 机器初始化阶段的正常双重复位，两次都落在复位向量上、寄存器/CSR 全零：

| 架构 | 复位签名 | 健康日志的形态 |
|---|---|---|
| x86_64 | `EIP=0000fff0 CS=f000`（实模式复位向量） | 共 56 行，两次复位在第 1 行和第 29 行 |
| riscv64 | `pc 0000000000001000`（virt 复位向量） | 共 420 行，两次复位在第 1 行和第 209 行（每个 dump ≈208 行，首尾相接） |

所以判据是"**多于 2 次**"，不是"有没有"。两次复位之后日志就该结束，后面不该再有东西。

## 判据二：保留 `-no-reboot`，用 `-d int`

不改运行参数，且能看到故障级联的每一步，代价是要读日志格式。

```bash
timeout 12 qemu-system-x86_64 -cdrom build/os.iso \
    -serial file:/tmp/vm_serial.txt -display none -no-reboot \
    -d int -D /tmp/vm_int.log

grep -n  "check_exception old: 0x8" /tmp/vm_int.log   # #DF 期间再故障 = 三重故障
grep -c  "cpl=3"                    /tmp/vm_int.log   # 用户态期间的异常条数
```

两个数都要看：`check_exception old: 0x8` 出现过就是确定的三重故障；`cpl=3` 的条数则更适合快速判断——**健康的 Lab7 是 1 条**（时钟中断本身，正常分发掉了），**崩溃的 Lab6 是 3 条**（时钟 → #PF → #DF 的级联）。

x86_64 上一次完整的三重故障级联长这样（Lab6 实测日志原文）：

```
0: v=20 e=0000 i=0 cpl=3 IP=002b:0000000000400027 pc=0000000000400027
1: v=0e e=0000 i=0 cpl=3 IP=002b:0000000000400027 CR2=0000000000000004
2: v=08 e=0000 i=0 cpl=3 IP=002b:0000000000400027
check_exception old: 0x8 new 0xd
```

读法：`v=20` 是时钟中断（在 `cpl=3` 落下来，IDT 分发本身正常）→ `v=0e` 是 #PF（`CR2=0x4`，往地址 0 附近写东西）→ `v=08` 是 #DF → `check_exception old: 0x8 new 0xd` 是处理 #DF 期间又来一个 #GP，也就是**三重故障**。这一行会是整个日志的最后一行。

## 唯一不能用的组合：`-no-reboot` + 只看 `-d cpu_reset`

**这个组合对三重故障是假阴性。** 本课程踩过这个坑，而且踩了两次。

三重故障在 QEMU 里是当作一次"复位请求"处理的，而 `-no-reboot` 的语义是"收到复位请求就**停机**，不要真的重启"。于是 QEMU 静静地把 CPU 停在那里，`-d cpu_reset` 日志里**一条复位记录都不会多**——就是启动阶段固有的那 2 次，和一个完全健康的内核跑出来的日志一模一样。

本课程所有 Lab 的标准运行命令都带 `-no-reboot`（它本来的用途是：让崩溃停在那里，不要重启刷掉现场）。所以如果你直接在标准命令后面加 `-d cpu_reset`，你查的就正好是这个假阴性组合。

## 红鲱鱼：`Servicing hardware INT`

`-d int` 日志里这类行**不是**内核的异常：

```
Servicing hardware INT=0x0e
Servicing hardware INT=0x08
```

它们是固件启动阶段的实模式 BIOS 调用，一个健康的内核日志里也照样有——实测 Lab6（崩溃）和 Lab7（健康）两份日志里这些行的条数完全一样（6 次 `INT=0x0e`、4 次 `INT=0x08`）。`INT=0x0e`/`INT=0x08` 这两个数字恰好和 #PF/#DF 的向量号相同，极容易误判。

**真正的内核异常只出现在带 `v=..` / `cpl=..` 字段的行里。**

## 实测数据表

下面每个数都是直接量出来的，不是推算。x86_64 用 `-cdrom build/os.iso`，riscv64 用 `-kernel build/kernel.elf`，超时窗口 12-15 秒。

| 二进制 | 判据一：`CPU Reset` / 横幅 | 判据二：`check_exception` / `cpl=3` | 结论 |
|---|---|---|---|
| Lab6 x86_64（**已知有缺陷**） | **72 次 / 35 次** | **1 次 / 3 条** | 崩溃：重启循环 |
| Lab6 riscv64 | 2 次 / 1 次 | 不适用 | 健康 |
| Lab7 x86_64 | 2 次 / 1 次 | 0 次 / 1 条 | 健康 |
| Lab7 riscv64 | 2 次 / 1 次 | 不适用 | 健康 |

四行都是用上面给出的命令原样跑出来的，两个架构各跑一遍，`timeout` 分别是 15 秒和 12 秒。同一行的数字在重复运行之间是稳定的（这个失效模式是确定性的，不是偶发竞争）。

Lab6 x86_64 那一行是这张表最重要的一行：**它证明这两个判据真的能检出故障。** 作为对照，同一个二进制用假阴性组合（`-no-reboot` + `-d cpu_reset`）查，得到的是"2 次，干净"。

Lab7 x86_64 的 `-d int` 日志里，同一个时钟中断照样在 `cpl=3` 落下来（`v=20 ... cpl=3 IP=0x400061`），但后面什么都没有——因为 Lab7 装了 TSS，硬件能取到合法的 RSP0。这是"判据能区分两个只差一个 TSS 的二进制"的直接证据。

## 元教训：检测方法本身也要验证

这是这份文档最该带走的一条，比任何具体命令都重要。

本课程第一次记录这个失效模式时，写下的检测方法是"`-d cpu_reset` + grep `CPU Reset`"。那个方法**只在一个健康的二进制上试过**，看起来"工作正常"（输出了 2 次，没有异常），于是就被当成可用的方法记了下来。结果一天之后，它被用来验证 Lab7，得出了"干净"的结论——而那个结论当时**没有任何证据支持**，因为那套方法对这类故障根本是瞎的。

**一个只在通过的二进制上试过的检测方法，什么都没有证明。** 要确认一个判据可用，必须让它至少对一个**已知坏**的二进制报警。本课程现在有一个现成的靶子：Lab6 x86_64 solution。任何新的"证明没崩"的方法，先拿它试，报不出来就说明方法不对。

这条和课程里另一条方法论是同一个道理：任何"这样改会怎样"的猜想，写进文档之前必须真的改代码跑一遍。区别只是这里猜的对象是**验证工具**而不是被测代码。

## riscv64 的差异

riscv64 **没有** x86_64 这个坑，原因是结构性的：riscv 的 trap 入口切换栈指针是**软件**做的——`trap_entry.S` 自己读 `sstatus.SPP` 判断来源特权级，再决定要不要换 `sp`。没有"硬件从某张表里取内核栈指针"这一层，也就不存在一张必须提前配好、配错了就静默崩溃的表。

判据一对 riscv64 同样适用（去掉 `-no-reboot`、数横幅）。判据二的 `check_exception` 是 x86 特有的日志格式，riscv64 上没有对应物——riscv 没有"三重故障"这个概念，异常嵌套的后果是 trap 到更高特权级或者进入不可恢复状态，形态不同。

## 什么时候必须做这个检查

- 任何 Lab 第一次让代码在 CPL=3 / U-mode 停留非零时长（本课程是 Lab6 起）。
- 任何 Lab 声称"内核在用户态代码跑完之后安全空转"。
- 任何 Lab 引入新的中断源，且该中断可能在用户态期间递交。
- 改动了 GDT/IDT/TSS（x86_64）或 `stvec`/trap 入口切栈逻辑（riscv64）之后。

不需要每次 `make test` 都跑——抽查一次就够，但**必须至少抽查一次**，且要用上面两个判据之一，不能用那个假阴性组合。
